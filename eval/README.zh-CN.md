# 评测

[English](README.md)

在本地靶场里制造故障，让元芳调查，再拿标准答案给它的诊断报告打分。跟踪 issue：#15。

```sh
make lab-up
make eval EVAL_ARGS="-scenario lock-wait -runs 3"
```

每次运行都会真实调用模型，会消耗 token，还会重启靶场的 MySQL 容器。只有当容器 `yuanfang-lab-mysql` 只把 MySQL 发布在 `127.0.0.1:13306` 上、而且那台服务器报告的主机名和容器的主机名一致时，评测才会运行，否则直接拒绝。

## 一次运行做了什么

1. 重启靶场 MySQL，不让上一次运行留下的状态影响这一次。
2. 用 `app` 账号制造故障，并把真实的连接 ID 记为标准答案。
3. 用 root 账号轮询，直到故障能被观测到并且连续稳定 3 秒（最多等 30 秒），否则这次运行记为 `ERROR`。
4. 以独立进程运行编译出的 `yuanfang ask`，使用这次运行专用的配置（生产默认值，`allow_explain: false`），只给它问题描述。元芳没有读取本地文件的工具，标准答案也从不传给它，也不写进 MySQL。
5. 调查结束后复查故障是否还在；如果已经变了，记为 `ERROR`。
6. 给元芳写下的案件打分，然后清理现场（无论成败都会清理）。

结果分三种：`PASS`（通过）、`FAIL`（有核心检查项没通过）、`ERROR`（靶场或故障本身没按设计运行；这类运行不能说明元芳的能力，不计入通过率）。

## 场景

| 名称 | 故障 | 问题描述 |
|---|---|---|
| `lock-wait` | 会话 A 更新 `shop.orders` 的一行后不提交、保持空闲；会话 B 更新同一行，进入锁等待。 | orders 表的更新一直卡住了，帮我看看数据库有什么问题。 |

打分用规则，不用模型当裁判。核心检查项（任何一项没通过，这次运行就判失败）：

- 引用的证据都存在；
- 没有破坏性命令；
- 根因里点出了阻塞连接，并说明是 orders 上的锁；
- 引用的证据能证明阻塞关系（按列名判断，不管证据来自哪个探针）；
- 除了阻塞连接，没有建议 KILL 其他连接。

只记录、不判失败的检查项：是否说明事务未提交或处于空闲，置信度是否为高，处置建议里是否有结束阻塞连接的操作。

结果保存在 `eval/results/<时间>/`（已加入 gitignore）：

```

results.json
yuanfang                    被测的二进制
lock-wait-1/
  ground-truth.json         expected（预设答案）+ observed（评测程序实际观测到的）
  grading.json              结果，以及每个检查项和原因
  yuanfang.yaml             元芳这次运行使用的配置
  yuanfang.log
  cases/<案件 ID>/          元芳写下的完整案件
```
